# Meta ignores x-api-key: fixing Awa's WhatsApp authentication

Saturn Studio's prospecting agent Awa fails with "invalid x-api-key" errors when sending WhatsApp messages to prospects scraped from Google Maps. The root cause is unambiguous: **Meta's WhatsApp Cloud API does not recognize the `x-api-key` header at all.** It authenticates exclusively via `Authorization: Bearer <token>`, meaning the token Awa sends is never read by Meta's servers, and the request is treated as unauthenticated. The "invalid x-api-key" error message does not originate from Meta -- it comes from a third-party gateway, proxy, or middleware sitting between Awa and `graph.facebook.com`. The fix requires switching authentication to Bearer tokens, verifying the endpoint hits Meta directly (not a BSP like YCloud or 360dialog), and ensuring the Graph API version in the URL path is between v21.0 and v26.0. Beyond the authentication bug, Awa's cold prospecting workflow faces structural constraints: Meta requires explicit opt-in before business-initiated messages, new accounts are capped at **250 unique recipients per day**, and spam reports from cold prospects trigger a quality feedback loop that can pause templates, reduce messaging tiers, and ultimately ban the account.

## Meta authenticates with Bearer tokens, never x-api-key

Meta's WhatsApp Cloud API uses a single authentication mechanism: the `Authorization: Bearer <ACCESS_TOKEN>` header sent with every request to `graph.facebook.com`. This is documented in Meta's official Get Started guide, which shows the exact curl syntax: `-H 'Authorization: Bearer <SYSTEM_USER_ACCESS_TOKEN>'` ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)). The Graph API also accepts the token as an `access_token` query parameter, though the header method is recommended. **No Meta documentation, Stack Overflow thread, or developer forum mentions Meta returning an "invalid x-api-key" error**, because Meta's servers simply do not read that header ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)).

The "invalid x-api-key" error Awa receives points to a third-party service intercepting the request. Several WhatsApp Business Solution Providers (BSPs) use `x-api-key` or similar custom headers: **YCloud** authenticates with `X-API-Key` and returns 401 UNAUTHORIZED for invalid keys ([YCloud: WhatsApp Errors](https://docs.ycloud.com/reference-link/whatsapp-errors)); **360dialog** uses a `D360-API-KEY` header ([360dialog: Error Messages](https://docs.360dialog.com/partner/support-and-updates/help-and-troubleshooting/error-messages)); **Namirial** requires both Basic Auth and `X-Api-Key`, returning "invalid-key" on mismatch ([Namirial: Authentication](https://docs.namirial.app/products/whatsapp/enterprise-documentation/developer-documentation/authentication)). If Awa's code was adapted from a BSP integration or routes through an API gateway (AWS API Gateway, Kong, Apigee), the `x-api-key` header is being validated by that intermediary, not by Meta. The fix is to audit Awa's request URL and headers: if the URL is not `graph.facebook.com`, the code is hitting a BSP; if it is, but an API gateway sits in front, the gateway's own key needs to be valid or removed.

Three token types exist for Meta's API. **Temporary tokens** from the App Dashboard expire within hours and are unsuitable for production. **System User tokens**, created in Meta Business Settings with `whatsapp_business_messaging` and `whatsapp_business_management` permissions, can be set to never expire and are the correct choice for Awa's `WHATSAPP_ACCESS_TOKEN` environment variable ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)). Token validity can be checked at any time using Meta's Access Token Debugger at `developers.facebook.com/tools/debug/accesstoken` ([ChakraHQ WhatsApp API Authorization Errors](https://chakrahq.com/help/chat/faqs/whatsapp-api-error-code-troubleshooting/whatsapp-api-authorization-errors)).

## Graph API versions v17-v20 are expired; use v21.0 or later

As of October 2026, **Meta Graph API v26.0 is the latest release**, and versions v21.0 through v26.0 are currently supported. Versions v17.0 through v20.0 have all expired: v17 expired September 2025, v18 in January 2026, v19 in May 2026, and v20 in September 2026 ([Versions - Graph API](https://developers.facebook.com/docs/graph-api/changelog/versions/)). Each version is guaranteed for at least two years from release, and Meta ships roughly three versions per year ([Ayrshare: Meta Graph API Versioning Survival Kit](https://www.ayrshare.com/solutions/meta-graph-api-versioning-survival-kit-staying-ahead-of-v21-v22-and-beyond/)).

A request to an expired version returns **HTTP 400 Bad Request** with error code 2635 -- a hard failure, not an automatic upgrade ([Ayrshare: Meta Graph API Versioning Survival Kit](https://www.ayrshare.com/solutions/meta-graph-api-versioning-survival-kit-staying-ahead-of-v21-v22-and-beyond/)). The correct endpoint format for Awa is `POST https://graph.facebook.com/v26.0/{PHONE_NUMBER_ID}/messages` with `Authorization: Bearer <token>` and `Content-Type: application/json` ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/)). The `{PHONE_NUMBER_ID}` is the numeric ID assigned to the phone number in WhatsApp Business Account settings (the `WHATSAPP_PHONE_NUMBER_ID` env var), not the phone number itself. Unversioned calls (no version in the URL path) default to the oldest version tied to the app and will silently break when that version expires.

Several breaking changes between v17 and v26 affect error handling and webhooks. Template error codes were split in v17 (paused templates return 132015 instead of 132001, disabled templates return 132016). In v23, error 132018 was added for invalid template parameters. In v24, status webhooks dropped the `conversation` object and `messaging_limit_tier` switched from phone-number-level to business-portfolio-level ([WhatsApp Changelog](https://developers.facebook.com/documentation/business-messaging/whatsapp/changelog)). The core `/messages` POST body structure, however, has remained stable across all these versions.

## Template message payloads require exact name and language matching

For business-initiated cold outreach, every first message must be a pre-approved template message -- freeform messages outside the 24-hour customer service window fail with error 131047 ([Meta Developer Docs: Send Messages](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages)). The minimum payload requires four top-level fields (`messaging_product`, `recipient_type`, `to`, `type`) and a `template` object with `name` and `language.code` ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/)). Templates with variables need a `components` array where each parameter matches the placeholder type and count defined in the approved template ([Template Fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview)).

A correct payload for Awa's Senegal prospecting, using a French-language template with two body variables, looks like this: `messaging_product` set to `"whatsapp"`, `to` set to the full E.164 number (e.g., `"+221781234567"`), `type` set to `"template"`, and the template object containing the approved name, language code `"fr"`, and a body component with positional text parameters ([Template Fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview)). Named parameters (using `parameter_name`) are safer than positional ones because they survive template edits that reorder placeholders. A successful send returns a response with `message_status` of `accepted`, `held_for_quality_assessment`, or `paused` ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/)).

The most common template send failures are: **132001** (template not found -- wrong name, wrong language code, or unapproved status), **132000** (parameter count mismatch), **132012** (parameter format mismatch), and **131009** (invalid phone number) ([Kaleyra Cloud API Error Codes](https://developers.kaleyra.io/docs/cloud-api-error-codes)). Template names and language codes are case-sensitive. For phone numbers, Meta "highly recommends" including the `+` prefix; without it, the business phone number's country code is prepended, which can cause misdelivery ([Meta Developer Docs: Send Messages](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages)). Senegalese mobile numbers follow the pattern `+2217XXXXXXXX` (country code +221, 9 digits starting with 7 for mobile), with no trunk prefix to strip ([Wikipedia: Telephone numbers in Senegal](https://en.wikipedia.org/wiki/Telephone_numbers_in_Senegal)).

## Cold prospecting faces a 250/day cap and aggressive quality enforcement

Meta's WhatsApp Cloud API enforces two rate limit layers: a per-second throughput cap (**80 messages per second** by default, upgradable to 1,000) and a daily unique-user limit set at the business portfolio level ([Meta Cloud API Overview](https://developers.facebook.com/docs/whatsapp/cloud-api/overview/)). New business portfolios start at **250 unique users per rolling 24-hour period** ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). Scaling to 2,000/day requires completing a "scaling path": verifying the business, having a partner verify it, or sending 2,000 quality messages in 30 days. Above 2,000, tiers auto-upgrade within 6 hours when at least half the current capacity is used with high-quality messages over 7 days ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). Adding more phone numbers does not increase the cap -- limits are portfolio-wide.

Quality enforcement operates through a feedback loop. Templates receive ratings of **Green** (high quality), **Yellow** (at risk), **Red** (near paused), or **Unknown** (new), based on user blocks, spam reports, and read rates ([Meta Template Quality Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-quality)). Meta does not publish the exact thresholds, though one vendor informally suggests keeping block rates below 2-3% to maintain Green ([ChakraHQ Article](https://chakrahq.com/article/prevent-whatsapp-business-restriction/amp/)). When quality degrades, templates can be paused or disabled, and the account's messaging tier can be reduced. Persistent violations lead to warnings, with appeals available within 90 days, and can escalate to temporary restrictions (30-day lift) or permanent bans ([Respond.io Blog](https://respond.io/blog/whatsapp-business-banned); [eGrow Blog](https://www.egrow.com/en/blog/meta-policy-whatsapp-business-2026)).

Meta's WhatsApp Business Messaging Policy explicitly requires **opt-in consent** before business-initiated messages -- implied consent is insufficient, and the opt-in must state the specific business and message types ([eGrow Blog](https://www.egrow.com/en/blog/meta-policy-whatsapp-business-2026)). Accepted methods include website checkboxes (unchecked by default), Click-to-WhatsApp ads, IVR prompts, and in-store QR codes. True cold outreach to contacts scraped from Google Maps, with no prior consent, violates this policy. Enforcement is reactive rather than preventive: Meta does not verify opt-in records proactively but acts on user complaints. Reports also indicate Meta is testing a new policy counting messages to non-responsive contacts against a monthly quota ([Android Headlines](https://www.androidheadlines.com/?p=1244582)). For Senegal specifically, the WhatsApp Business API is available with no country-specific restrictions, though local data protection law (Loi n 2008-12, enforced by the CDP) imposes additional consent requirements ([Kolonell Blog](https://kolonell.com/en/blog/whatsapp-business-api-meta-pricing-senegal-2026)).

## Conclusion

Awa's "invalid x-api-key" error is a configuration bug, not an API issue: the code is either hitting a third-party BSP endpoint or routing through an API gateway that expects its own key. The immediate fix is to send `Authorization: Bearer <SYSTEM_USER_ACCESS_TOKEN>` directly to `https://graph.facebook.com/v26.0/{PHONE_NUMBER_ID}/messages`. The deeper challenge is structural: cold-messaging Google Maps prospects without opt-in violates Meta's policy and exposes the account to a quality degradation spiral that starts with paused templates and ends with a banned number. The most viable path forward is to convert Awa from a cold outreach agent into an opt-in acquisition agent -- using Click-to-WhatsApp ads, landing pages, or QR codes to collect consent first, then sending personalized template messages within policy. This preserves the prospecting workflow while staying within Meta's enforcement framework and Senegal's data protection requirements.
