# Meta's WhatsApp Cloud API demands Bearer tokens, not x-api-key

The "invalid x-api-key" error plaguing Awa's WhatsApp integration does not come from Meta. Meta's WhatsApp Cloud API authenticates exclusively via `Authorization: Bearer <token>` and has no knowledge of the `x-api-key` header -- any request carrying only that header arrives unauthenticated and fails with an OAuthException (error code 0, HTTP 401). The error message itself -- "invalid x-api-key" -- originates from a third-party gateway or middleware sitting between the codebase and Meta's graph.facebook.com endpoint, most likely a BSP (Business Solution Provider) such as YCloud, 360dialog, or Evolution API, or an intermediary API gateway like AWS API Gateway or Kong. Fixing this requires identifying which service the code is actually calling, then either configuring the correct API key for that service or switching to Meta's direct Cloud API with a System User Bearer token. Beyond authentication, a production-grade WhatsApp prospecting integration must handle API versioning (v21.0 through v26.0 as of October 2026), strict template message formatting, tiered messaging limits starting at 250 unique recipients per day, and Meta's anti-spam enforcement loop that can pause templates and ban accounts. For Saturn Studio's Awa agent targeting Senegal (+221), the technical path is clear but the policy terrain is treacherous: true cold outreach without opt-in violates Meta's Business Messaging Policy, and enforcement operates through a quality feedback system with unpublished thresholds.

## The x-api-key error points to a third-party gateway, not Meta

Meta's Graph API reads authentication from exactly two places: the `Authorization: Bearer` header or an `access_token` query parameter ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)). It ignores any other header, including `x-api-key`. When a request arrives without a recognized credential, Meta returns **error code 0 (OAuthException)** with HTTP 401 and a message referencing authentication failure -- never "invalid x-api-key" ([ChakraHQ WhatsApp API Authorization Errors](https://chakrahq.com/help/chat/faqs/whatsapp-api-error-code-troubleshooting/whatsapp-api-authorization-errors)). No search across Meta's developer documentation, Stack Overflow, or developer forums surfaces a single instance of Meta returning an "invalid x-api-key" response.

The error therefore originates upstream. Several WhatsApp BSPs authenticate with `x-api-key` or similar custom headers: **YCloud** uses `X-API-Key` and returns 401 UNAUTHORIZED for invalid keys ([YCloud: WhatsApp Errors](https://docs.ycloud.com/reference-link/whatsapp-errors)); **360dialog** uses its own `D360-API-KEY` header ([360dialog: Error Messages](https://docs.360dialog.com/partner/support-and-updates/help-and-troubleshooting/error-messages)); **Namirial** requires both Basic Auth and `X-Api-Key`, returning "invalid-key" when the value is wrong ([Namirial: Authentication](https://docs.namirial.app/products/whatsapp/enterprise-documentation/developer-documentation/authentication)); and **Evolution API**, an open-source WhatsApp gateway, also supports `x-api-key` ([Traccar Forum: Evolution API](https://www.traccar.org/forums/topic/authentication-method-x-api-key-for-sending-notifications-using-the-evolution-api/)). The most common scenario is code originally written for a BSP that was migrated -- or intended to be migrated -- to Meta's direct Cloud API without updating the authentication header. The fix is surgical: identify the base URL in the HTTP client configuration, and if it points to graph.facebook.com, replace `x-api-key` with `Authorization: Bearer <SYSTEM_USER_TOKEN>`.

## Bearer tokens come in three types, and only one belongs in production

Meta issues three kinds of access tokens. **Temporary user tokens**, generated from the App Dashboard's WhatsApp API Setup page, expire within roughly 24 hours (Meta's docs say only "expires quickly") and are strictly for testing ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)). **System User access tokens**, created under Meta Business Settings > System Users, can be set to never expire and are the standard for production integrations; they require assigning the app with "Manage app" permission and granting `business_management`, `whatsapp_business_messaging`, and `whatsapp_business_management` scopes ([Meta WhatsApp Cloud API Get Started](https://developers.facebook.com/docs/whatsapp/cloud-api/get-started)). **Business Integration System User tokens** serve Tech Providers and Solution Partners rather than direct integrators ([WooCommerce: Meta System User Access Token](https://woocommerce.com/?p=18734006930318)). System User tokens with "Never" expiry are effectively permanent unless manually revoked, though Meta reserves the right to invalidate any token at any time ([Digital Inspiration: WhatsApp API Token](https://digitalinspiration.com/docs/document-studio/apps/whatsapp/token)). The **Access Token Debugger** at developers.facebook.com/tools/debug/accesstoken is the definitive tool for verifying a token's type, expiry, and permissions ([ChakraHQ WhatsApp API Authorization Errors](https://chakrahq.com/help/chat/faqs/whatsapp-api-error-code-troubleshooting/whatsapp-api-authorization-errors)).

When tokens fail, Meta returns structured JSON with specific error codes: **code 0 (AuthException)** for general authentication failure (expired, revoked, or missing token), **code 190** for a token whose expiry time has specifically passed, and **codes 200-299** for permission errors where the token exists but lacks required scopes ([ChakraHQ WhatsApp API Authorization Errors](https://chakrahq.com/help/chat/faqs/whatsapp-api-error-code-troubleshooting/whatsapp-api-authorization-errors)). Error-handling code should match on the `code` and `details` fields in the JSON response, not on HTTP status codes or error titles.

## API versions expire on a two-year clock, and expired calls fail hard

The message-sending endpoint follows the format `POST https://graph.facebook.com/v{VERSION}/{PHONE_NUMBER_ID}/messages` with `Authorization: Bearer <token>` and `Content-Type: application/json` ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/)). As of October 2026, **v26.0 is the latest release** (July 29, 2026) and **v21.0 through v26.0 are supported**; v17.0 through v20.0 have all expired ([Versions - Graph API](https://developers.facebook.com/docs/graph-api/changelog/versions/)). Each version is guaranteed for at least two years from release ([Ayrshare: Meta Graph API Versioning Survival Kit](https://www.ayrshare.com/solutions/meta-graph-api-versioning-survival-kit-staying-ahead-of-v21-v22-and-beyond/)). Calling an expired version returns **HTTP 400 Bad Request** with a subcode indicating the version is no longer supported; third-party sources report this as error code 2635, though Meta's own docs do not explicitly document this code ([Ayrshare](https://www.ayrshare.com/solutions/meta-graph-api-versioning-survival-kit-staying-ahead-of-v21-v22-and-beyond/)). This is a hard failure -- there is no automatic upgrade to a newer version.

The `{PHONE_NUMBER_ID}` in the URL is the numeric ID assigned to the phone number in WhatsApp Business Account settings, not the phone number itself. The `/v1/messages` path seen in some older documentation belongs to the deprecated on-premises API ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/)). Notable breaking changes across versions include: error code splits in v17 (`132015`/`132016` replacing `132001` for paused/disabled templates), authentication template structure changes in v21, the new `132018` error for invalid template parameters in v23, and removal of the `conversation` object from status webhooks in v24 ([WhatsApp Changelog](https://developers.facebook.com/documentation/business-messaging/whatsapp/changelog)). The core message-sending payload structure, however, has remained stable across all versions from v17 through v26.

## Template message payloads require exact name, language, and parameter alignment

Every business-initiated message outside the 24-hour customer service window must use a pre-approved template ([Meta Developer Docs: Send Messages](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages)). Attempting a freeform message outside this window returns **error 131047** ([Kaleyra Cloud API Error Codes](https://developers.kaleyra.io/docs/cloud-api-error-codes)). The minimum payload requires four top-level fields -- `messaging_product` (set to `"whatsapp"`), `to` (recipient phone in E.164), `type` (set to `"template"`), and a `template` object containing `name` and `language.code` -- plus a `components` array when the template includes variables ([Messages - WhatsApp Cloud API Reference](https://developers.facebook.com/docs/whatsapp/cloud-api/reference/messages/); [Template Fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview)).

Template names and language codes are **case-sensitive**; `"fr"` and `"FR"` are different values, and a mismatch produces **error 132001** (template does not exist) ([Kaleyra Cloud API Error Codes](https://developers.kaleyra.io/docs/cloud-api-error-codes)). Parameters can be passed positionally (order matches `{{1}}`, `{{2}}`, etc.) or with named `parameter_name` fields; named parameters are safer because they survive template edits that reorder placeholders ([Template Fundamentals](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/overview)). Other common failures include **132000** (parameter count mismatch), **132012** (parameter format mismatch), and **132005** (hydrated text exceeds the length limit after variable substitution) ([Kaleyra Cloud API Error Codes](https://developers.kaleyra.io/docs/cloud-api-error-codes)). Templates are capped at **250 per WhatsApp Business Account** with a **1,024-character** body limit ([360dialog docs](https://docs.360dialog.com/partner/messaging/template-messages)). For Senegal, phone numbers follow the pattern `+221` plus 9 digits starting with 7 (mobile) or 3 (landline) -- validation regex: `/^\+221[37]\d{8}$/` -- and there is no trunk prefix to strip ([sent.dm: Senegal Phone Numbers](https://www.sent.dm/resources/sn); [Wikipedia: Telephone numbers in Senegal](https://en.wikipedia.org/wiki/Telephone_numbers_in_Senegal)). Meta "highly recommends" including the `+` prefix; omitting it causes the sender's country code to be prepended, which can misroute the message entirely ([Meta Developer Docs: Send Messages](https://developers.facebook.com/docs/whatsapp/cloud-api/guides/send-messages)).

A representative payload for Awa's Senegalese prospecting use case:

```json
{
  "messaging_product": "whatsapp",
  "recipient_type": "individual",
  "to": "+221781234567",
  "type": "template",
  "template": {
    "name": "prospection_intro",
    "language": { "code": "fr" },
    "components": [
      {
        "type": "body",
        "parameters": [
          { "type": "text", "parameter_name": "first_name", "text": "Moussa" },
          { "type": "text", "parameter_name": "company", "text": "votre entreprise" }
        ]
      }
    ]
  }
}
```

## Rate limits tier from 250 to Unlimited, and quality ratings control the climb

WhatsApp Cloud API enforces two distinct rate limits. The **throughput cap** defaults to **80 messages per second** per phone number, upgradable to 1,000 mps based on quality ([Meta Cloud API Overview](https://developers.facebook.com/docs/whatsapp/cloud-api/overview/)). The **daily messaging limit** caps unique users contactable outside the customer service window within a rolling 24-hour period, starting at **250 unique users** for new business portfolios, then progressing through **2,000, 10,000, 100,000, and Unlimited** tiers ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). These limits are set at the **business portfolio level** and shared across all phone numbers in the portfolio -- adding more numbers does not increase the cap ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)).

Scaling from 250 to 2,000 requires completing one of three "scaling paths": business verification, partner verification, or sending 2,000 quality-delivered messages to unique numbers within 30 days ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). Above 2,000, automatic upgrades occur within **6 hours** when two conditions hold: high-quality messages across all numbers and templates, and usage of at least half the current tier over the past 7 days ([Meta Messaging Limits Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/messaging-limits)). For cold prospecting, the daily unique-user limit is the binding constraint long before throughput matters. Exceeding throughput returns **error 130429** (HTTP 429); the recommended retry strategy is exponential backoff with jitter ([Meta Cloud API Overview](https://developers.facebook.com/docs/whatsapp/cloud-api/overview/)).

Quality ratings operate at both the template and phone number level. Templates are rated **Green** (healthy), **Yellow** (at risk of pausing), **Red** (imminent pausing), or **Unknown** (new, no data) based on user feedback -- blocks, reports, and read rates ([Meta Template Quality Documentation](https://developers.facebook.com/documentation/business-messaging/whatsapp/templates/template-quality)). A paused template cannot be sent until it recovers, with third-party sources estimating **7 days** for recovery ([Exotel Developer Docs](https://developer.exotel.com/docs/whatsapp-support/quality-rating)). At the account level, persistent low quality can **reduce messaging tiers** and ultimately lead to a WABA ban ([eGrow Blog](https://www.egrow.com/en/blog/meta-policy-whatsapp-business-2026)). Meta does not publish the exact block-rate or report-rate thresholds that trigger each quality level; one vendor informally suggests keeping block rates below **2-3%** but this is unverified ([ChakraHQ Article](https://chakrahq.com/article/prevent-whatsapp-business-restriction/amp/)).

## Cold outreach is policy-prohibited but reactively enforced -- a calculated risk

Meta's WhatsApp Business Messaging Policy requires **explicit opt-in consent** before sending business-initiated messages. Consent must specify the business name, message types, and be documented with method, timestamp, and exact wording; generic email or SMS opt-ins do not carry over to WhatsApp ([eGrow Blog](https://www.egrow.com/en/blog/meta-policy-whatsapp-business-2026)). Accepted methods include website checkboxes (unchecked by default), click-to-WhatsApp ads, IVR prompts, and in-store sign-ups ([ChakraHQ Compliance Guide](https://chakrahq.com/help/learning-centre/whatsapp-business-api/understanding-compliance-policies-and-consent)). Every marketing message must include an **opt-out mechanism** (e.g., "Reply STOP to unsubscribe") and opt-outs must be honored immediately ([ChakraHQ Compliance Guide](https://chakrahq.com/help/learning-centre/whatsapp-business-api/understanding-compliance-policies-and-consent)).

Enforcement is reactive, not preventive: the API will deliver a template message to any valid WhatsApp number regardless of prior consent. The consequences arrive through the quality feedback loop. Recipients who block or report messages degrade template quality ratings, which can cascade into template pausing, tier downgrades, and ultimately account restrictions or permanent bans ([Respond.io Blog](https://respond.io/blog/whatsapp-business-banned)). WhatsApp's algorithms also detect patterns resembling automation or unsolicited outreach and can impose temporary restrictions independently of user reports ([Prospeo: WhatsApp Cold Outreach](https://prospeo.io/s/whatsapp-cold-outreach)). Reports indicate Meta is testing new policies that count messages to **non-responsive contacts** against a monthly quota, though the exact parameters and rollout status remain unconfirmed ([Android Headlines](https://www.androidheadlines.com/?p=1244582); [TechEconomy.ng](https://www.techeconomy.ng/whatsapp-sets-messaging-limits-curb-spam)).

Senegal is not on Meta's restricted country list, and standard global policies apply without additional constraints from Meta's side ([Deskpro Support](https://support.deskpro.com/en-US/guides/admin-guide/channels/whatsapp/whatsapp-country-restrictions)). Business verification in Senegal can use local Registre du Commerce and NINEA documents ([Kolonell Blog](https://kolonell.com/en/blog/whatsapp-business-api-meta-pricing-senegal-2026)). However, Senegal's own data protection law (Loi n 2008-12, enforced by the CDP) imposes consent requirements for marketing communications that parallel the spirit of GDPR, and local legal counsel should be consulted for compliance.

## Conclusion

The "invalid x-api-key" error is a definitive sign that Awa's HTTP requests are hitting a third-party service -- not Meta's Cloud API directly. The immediate fix is to audit the base URL and authentication headers in the code, switch to `Authorization: Bearer <SYSTEM_USER_TOKEN>` for graph.facebook.com calls, and verify the token with Meta's Access Token Debugger. The deeper architectural concern for a prospecting agent is that WhatsApp's quality feedback loop creates a self-regulating system with no published safety thresholds: cold outreach that triggers even modest block rates will compound into template pausing, tier downgrades, and potential account bans within days. The most sustainable approach for Awa is to treat WhatsApp as a second-touch channel -- using click-to-WhatsApp ads, landing pages, or web forms to collect explicit opt-in before sending the first template message -- rather than as a cold outreach tool. This transforms a policy violation into a compliant workflow while preserving the personalization and high open rates that make WhatsApp valuable for prospecting in the Senegalese market.
